## Background

PDF citation の LLM 出力契約を、locator 直接生成から rangeId 参照へ変更する計画を記録する。

## Result

- **Adopted Protocol**: LLM 生成中は `rangeId` だけを citation block に書かせ、保存前の `normalizePdfCitationBlocks()` で registry から `locator` へ解決する。保存形式は既存の `::: citation {"locator":{...}}` canonical Markdown を維持する。
- **History Boundary**: 次 turn の LLM 入力には保存済み locator block をそのまま渡さず、履歴 adapter で citation block を削除または短い marker にし、別枠の `Previous PDF evidence` として `evidenceId`、source label、rawText または evidenceText、任意の `usedFor` / `claim` を渡す。
- **Implementation Order**: types / per-request registry、tool return、normalization、prompt、history adapter、tests、docs の順で入れる。UI は保存後 `locator` canonical を読めれば最小変更で済む。

## Detail

### Background

現状の PDF citation は、LLM が最終回答に `::: citation {"locator":...}` を直接書く契約である。`locator` には `libraryID`、`attachmentKey`、`start`、`end` が含まれるため、LLM が tool result の offset を手書き、転記、または過去 turn の block から模倣できてしまう。

この方式では、引用範囲の選択責務と永続化 locator の生成責務が LLM 側で混ざる。`rangeId` 方式では、LLM は「今回 tool で確認した範囲を参照する」だけにし、永続化に必要な locator は plugin が registry から解決する。

### Adopted Policy

- **Generation-time reference**: LLM の最終回答は `::: citation {"rangeId":"r_..."}` を書く。
- **Persistence format**: chat history に保存する Markdown は既存形式の `::: citation {"locator":{...}}` に正規化する。
- **Next-turn context**: 保存済み citation block はそのまま LLM に渡さない。履歴 adapter が citation block を消す、または短い marker に置換し、別途 `Previous PDF evidence` として evidence 情報を渡す。
- **Locator secrecy**: LLM には `locator.start` / `locator.end` を見せない。新規生成 protocol では legacy locator direct generation を使わせない。
- **Compatibility**: legacy locator block は normalize 可能に残す。ただし新規 prompt と tool protocol は `rangeId` のみを正規経路にする。

### Specification

1. `read_pdf_text_range` returns `rangeId`.
   - tool result includes `rangeId`, `text`, `before`, `after`, `textVersion`, and display-safe source metadata if needed.
   - tool result does not expose final `locator.start` / `locator.end` to the LLM in the new protocol.
2. A per-request range registry stores each read range.
   - entry shape: `{ rangeId, locator, rawText/text, before, after, textVersion }`.
   - scope: one `sendMessageToLlm()` request, including all tool-loop rounds and final normalization.
   - ownership: plugin-created IDs only; LLM-provided IDs are never trusted as registry entries.
3. The final answer uses `rangeId`.
   - accepted new block: `::: citation {"rangeId":"r_..."}` with an empty body.
   - block body remains untrusted; render text is generated by the existing citation render path after resolution.
4. `normalizePdfCitationBlocks()` resolves and canonicalizes.
   - for `rangeId`, look up the registry entry, validate text freshness and non-empty range, render display text, and rewrite to `::: citation {"locator":{...}}`.
   - saved locator includes plugin-computed `textVersion`.
   - for legacy `locator`, keep the current normalize path for compatibility.
5. The history adapter converts saved citations before the next request.
   - `toLangChainMessages()` or a new wrapper used by `buildMessages()` should not pass raw saved citation blocks to the next LLM call.
   - adapter output should include `Previous PDF evidence` records: `evidenceId`, source label, `rawText` or `evidenceText`, and optional `usedFor` / `claim`.
   - previous evidence should not include locator offsets.

### Failure Semantics

- **Unknown `rangeId`**: drop the citation block, increment dropped diagnostics, and log a warning. Do not fall back to LLM-supplied locator fields in the same block.
- **Stale `textVersion`**: if current attachment text hash differs from the registry entry, drop the block or re-read by plugin-owned locator and mark stale only if the product decision explicitly accepts stale canonicalization. Default should be drop during new normalization.
- **Empty range**: reject during tool return or normalization; do not create a registry entry for an empty `text`.
- **`rangeId` without tool usage**: reject as invalid. This includes blocks generated when no PDF tool was available or no successful `read_pdf_text_range` call registered the ID.
- **Legacy locator direct generation**: normalize for backward compatibility, but record diagnostics so prompt regressions are visible. New-protocol prompts should instruct that locator JSON is invalid for newly generated citations.

### Implementation Plan

1. **Types and registry**
   - Add `PdfCitationRangeRegistry`, `PdfCitationRangeEntry`, and `PdfCitationRangeId` near `src/modules/pdfCitation.ts` or a sibling module.
   - Generate request-local IDs with a short random token, such as `r_7k9p2x4q`, so examples do not teach the LLM to invent predictable sequential IDs.
2. **Tool return**
   - Thread the registry into `createPdfCitationTools()`.
   - Update `readPdfTextRange()` tool wrapper to register `{ locator, rawText/text, before, after, textVersion }` and return `rangeId`.
   - Keep internal `readPdfTextRange()` usable for normalization and UI recovery.
3. **Normalization**
   - Extend citation JSON parsing to accept either `{ "rangeId": "r_..." }` or `{ "locator": ... }`.
   - Resolve `rangeId` through the per-request registry before calling the existing render path.
   - Preserve canonical saved Markdown with `locator`.
4. **Prompt changes**
   - Update `addon/prefs.js` and `buildCitationAttachmentContext()` so LLM instructions show `rangeId` citation blocks, not locator blocks.
   - Explicitly say not to output `locator`, `start`, `end`, `rawText`, `source`, or `textVersion`.
5. **History adapter**
   - Replace direct `toLangChainMessages(history)` usage for chat requests with an adapter that strips or marks citation blocks and appends `Previous PDF evidence`.
   - Recover raw evidence from saved locators via plugin code, not from LLM-written display text.
6. **Tests**
   - Add focused unit tests for range registry resolution, legacy compatibility, failure cases, and history conversion.
   - Add integration-ish tool-loop tests if the existing test infrastructure can invoke `sendMessageToLlm()` with fake tools/model responses.
7. **Docs**
   - Update `docs/pdf_citation_format.md` after implementation so it distinguishes generation-time `rangeId` from saved canonical `locator`.

### Candidate Files

- `src/modules/pdfCitation.ts`: tool definitions, registry, block parser, normalization, locator recovery utilities.
- `src/modules/llm/chat.ts`: per-request registry lifecycle, tool loop threading, prompt attachment context, diagnostics.
- `src/modules/llm/langChainMessages.ts`: history adapter or helper used to convert stored messages for LLM context.
- `src/modules/reader/chatSession.ts`: call site that selects truncated history and sends it to `sendMessageToLlm()`.
- `addon/prefs.js`: default system prompt and PDF evidence rules.
- `docs/pdf_citation_format.md`: public protocol documentation.
- `src/modules/llm/citationRenderService.ts`: likely unchanged except for input type naming; it already rejects locator JSON in render output.
- `src/modules/reader/ui.ts`: likely minimal change because saved canonical locator blocks continue to render and hover-recover through existing code.

### Test Plan

- **Normalization unit tests**: `rangeId` resolves to canonical locator; unknown `rangeId`, empty range, stale text, nested citation, and locator-without-tool cases are dropped with warnings.
- **Registry unit tests**: IDs are per request, unique within a request, and cannot be created by model output alone.
- **History adapter unit tests**: saved `::: citation {"locator":...}` blocks are not passed raw to the next LLM call; `Previous PDF evidence` contains evidence text and source label but no offsets.
- **Legacy compatibility tests**: existing locator blocks still normalize and render.
- **Tool-loop tests**: if existing infra allows fake LangChain models, verify successful `read_pdf_text_range` call followed by `rangeId` block produces saved locator canonical Markdown.
- **UI verification**: minimal if saved Markdown remains locator canonical; existing render and hover recovery should continue to work.

### Non-goals and Residual Risks

- The protocol does not fully solve LLM selection of an inappropriate evidence range. It only prevents manual offset transcription and mimicry.
- This is weaker than a full evidence-card provenance model because the final answer still chooses where to attach the registered range.
- `Previous PDF evidence` can pressure context size and may encourage overuse of older evidence. The adapter should cap evidence count and prefer recent or explicitly referenced evidence.
- Legacy compatibility keeps a direct locator path alive, so diagnostics and prompt tests are needed to detect new-model regression.
